## Part 2 — ADD Tier-1 features (all of them, still lean)

### T1.1 Background jobs + completion push
**Problem:** Long browser/doc/terminal work forces the user to watch chat.

**Add (lightweight):**
- Local agent: simple **in-process job registry** (map/id + status + result path + summary). No Redis.
- Long-running tool sequences can be marked as a job; status: `queued | running | done | failed | cancelled`.
- On **done/failed**: push via **existing FCM/local notification path** already used for security alerts:
  - payload: `type: task_complete | task_failed`, title, short summary, artifact path if any, job id.
- Mobile: handle notification open → jump to chat/artifacts for that result if already supported; else show notification + message in chat stream.
- Optional: one agent/chat message “Job N finished” so history stays coherent.

**Weight bound:** memory/disk JSON only; jobs don’t survive complex distributed locking in v1.

### T1.2 Playbooks
**Problem:** Repeat workflows require re-prompting every time.

**Add (minimal):**
- On-disk playbooks: e.g. `local-agent/playbooks/*.json`  
  `{ "id", "name", "steps": [ { "type": "agent_prompt" | "tool", ... } ] }`
- Tool or command: `list_playbooks`, `run_playbook` (add tools; don’t remove others).
- Mobile: simple entry to run by name/id (button or command like `/play morning` / picker if low-cost in existing UI).
- Steps run sequentially through **existing** agent/tool loop; on failure, stop and report (no heavy workflow engine).
- Seed 1–2 example playbooks (e.g. “status report”, “quick system summary”) that use existing tools only.

### T1.3 Natural summary TTS (mobile only, summaries only)
**Problem:** Current `flutter_tts` sounds robotic for long reads.

**Add (weight-bounded):**
- Prefer **edge_tts** (or equivalent light package) for **task summaries / completion summaries only**.
- Fallback: existing `flutter_tts` if offline or edge fails.
- Do **not** speak every log line or full tool dump.
- Do **not** bundle large offline models (no Piper/Kokoro requirement in this pass).
- Reuse existing `_speak` call sites: route **summary** text through new helper; leave alerts on system TTS if simpler.

### T1.4 Document quality gates
(Covered in 1.2 — must be implemented as a hard gate, not a suggestion.)

- Min substance checks: body length and/or presence of table/image when IR/prompt implies report/audit/blueprint.
- Clear error string for the LLM to retry with structure.
- Optional: score hook already in `doc_quality.py` — call or mirror lightly; don’t build a new QA product.

### T1.5 Mobile approve for dangerous actions
**Problem:** Full autonomy is scary without a confirm step.

**Add:**
- Local agent maintains a small set of **dangerous patterns** (configurable list): e.g. recursive delete, `git push`, format, mass uninstall, send-mail, force push — match on tool name + command string heuristics.
- When matched: **do not execute yet**; emit event to mobile: `type: approval_required`, action summary, job/command id, timeout (e.g. 45–60s).
- Mobile: modal/dialog **Allow / Deny** (reuse notification + in-app banner if modal is heavy).
- On Allow → agent executes; on Deny/timeout → abort and report.
- Safe default: if mobile unreachable, **deny** (fail closed) or policy flag — document choice; prefer fail closed for v1.
- Do not block harmless `run_terminal` (dir listing, echo, git status).
